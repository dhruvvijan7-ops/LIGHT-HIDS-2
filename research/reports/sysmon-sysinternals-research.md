**Claim 2.3 — event timestamps.**
- **VERIFIED:** Sysmon docs: "Event timestamps are in UTC standard time" *(quote)*. - **VERIFIED:** In the Windows event XML schema the wall-clock stamp is the `TimeCreated` element's required `SystemTime` attribute (type `dateTime`, "The system time of when the event was logged"). Provenance: https://learn.microsoft.com/en-us/windows/win32/wes/eventschema-timecreated-systempropertiestype-element (accessed 2026-10-08); schema context: https://learn.microsoft.com/en-us/windows/win32/wes/eventschema-systempropertiestype-complextype (accessed 2026-10-08).
- **INFERRED:** therefore Sysmon event XML contains `<TimeCreated SystemTime="…">` in UTC — follows from the two VERIFIED facts; not shown verbatim in Sysmon docs.

**Claim 2.4 — documented event IDs and fields.**
- **VERIFIED:** Event IDs with descriptions are documented: 1 Process creation, 3 Network connection (disabled by default), 11 FileCreate (created or overwritten), 22 DNSEvent/DNS query (added for Windows 8.1; not on Windows 7-), plus 2, 4–10, 12–21, 23–29, 255. Provenance (both pages list IDs 1/3/11/22): https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon (accessed 2026-10-08); https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/sysmon-events (accessed 2026-10-08).
- **VERIFIED — field detail level differs by page:** the events page lists *field categories* per event (e.g. ID 1: full command line, parent process, cryptographic hashes, Process GUID; ID 3: source/destination addresses, ports, protocols, Process GUID); the download page gives per-event narrative fields (e.g. ID 1 `ProcessGUID`, hash in `HashType`; ID 3 `ProcessId`/`ProcessGuid`, host names, IPs, ports, IPv6 status). Full per-field schemas are available via `sysmon -s` (schema dump; download page shows the RawAccessRead schema example with `UtcTime`, `ProcessGuid`, `ProcessId`, `Image`, `Device`). Provenance: both URLs above (accessed 2026-10-08).
- **VERIFIED:** Filter tag ↔ event ID mapping table (1 ProcessCreate, 3 NetworkConnect, 11 FileCreate, 22 DnsQuery, …; IDs 4 and 16 "cannot be filtered"). Provenance: https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon and https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/sysmon-configuration-files (accessed 2026-10-08).

**Claim 2.5 — configuration XML structure.**
- **VERIFIED:** Config is XML with a `schemaversion` attribute on the `<Sysmon>` tag; global entries sit directly under `Sysmon`, filters under `<EventFiltering>`; `schemaversion` is independent of the binary version. Example shown with `schemaversion="4.82"`. Provenance: https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon (accessed 2026-10-08).
- **VERIFIED:** Include/exclude semantics: `onmatch="include"` logs only matched events; `onmatch="exclude"` logs all except matches; exclude wins over include when both exist for an event; same-field rules OR, different-field rules AND. Provenance: https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon; https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/sysmon-configuration-files (both accessed 2026-10-08).
- **VERIFIED:** Condition table includes `less than` ("Lexicographical comparison is less than zero") and `more than` ("Lexicographical comparison is more than zero"), alongside `is`, `is any`, `is not`, `contains`, `contains any/all`, `excludes*`, `begin with`, `end with`, `not begin with`, `not end with`, `image`. Provenance: https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon (accessed 2026-10-08); condensation "less than / more than — Lexicographical comparison" also on https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/sysmon-configuration-files (accessed 2026-10-08).
- **VERIFIED:** `image` condition documented as "Match an image path (full path or only image name). For example: `lsass.exe` will match `c:\windows\system32\lsass.exe`" *(quote)*; config-page table calls it "Path-aware image matching". Provenance: both URLs above (accessed 2026-10-08).
- **INFERRED:** therefore the `image` condition supports **partial/path-tail matching** (bare image name matches the full path). The exact downstream phrasing "can produce a partial list of matched entries" is **not** documented wording — UNVERIFIED as written; what is documented is name-vs-full-path matching.
- **VERIFIED:** `<RuleGroup name="…" groupRelation="and|or">` overrides default rule combination per event; rules can be named (`name=` attribute) for audit context. Provenance: both URLs above (accessed 2026-10-08).
- **VERIFIED:** Config change generates Event ID 16 ("Whenever the Sysmon configuration is updated, Sysmon generates a configuration change event"). Provenance: https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/sysmon-configuration-files (accessed 2026-10-08).

## §SYSMON-4 — Config-to-detection pipeline: what community configs imply for a backend like Sentinel

*Topic choice: how SwiftOnSecurity/sysmon-modular content and Microsoft's documented configuration semantics determine what telemetry a Windows-first offline backend can ever see. All claims below are drawn from sources already cited; no fabricated data.*

- **VERIFIED — Microsoft's position on what configs are for:** configuration files "Do not detect threats / Do not generate alerts / Do not classify behavior / Do not replace SIEM or EDR logic … They define what evidence exists, not how it is interpreted" *(quote, paraphrased list)*; and "Once telemetry is excluded, it cannot be recovered retroactively" *(quote)*. Provenance: https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/sysmon-configuration-files (accessed 2026-10-08). ⇒ Detection logic must live downstream (Sentinel), not in the Sysmon config.
- **VERIFIED — Microsoft's config design guidance:** start broad and refine; exclude known benign activity; preserve investigative context; avoid over-specific rules; restrictive/unoptimized configs may generate high event volume — test before broad deployment. Provenance: https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/sysmon-configuration-files and https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/how-to-enable-sysmon (accessed 2026-10-08).
- **VERIFIED — Microsoft points users at the two community repos** (see §SYSMON-3(a)/(b) provenance): SwiftOnSecurity = "Default high-quality Sysmon event configuration"; sysmon-modular = "Modular Sysmon configuration with MITRE ATT&CK coverage"; also lists trustedsec/SysmonCommunityGuide. Provenance: https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/how-to-enable-sysmon (accessed 2026-10-08).
- **VERIFIED — filtering decides backend visibility:** only events surviving `<EventFiltering>` reach the channel; exclude beats include; RuleGroup sets AND/OR per event; IDs 4/16 unfilterable (service state, config change are always available for auditing config drift). Provenance: §SYSMON-2 URLs (accessed 2026-10-08).
- **VERIFIED — version skew is real:** SwiftOnSecurity config declares `schemaversion="4.50"` and "REQUIRED: Sysmon version 13 or higher"; Microsoft's examples use `4.82` (download page) and `4.90` (how-to-enable); sysmon-modular generates per-target configs for 15.21/14.16/13.34/12.03 while the current standalone Sysmon is v15.22. Provenance: `SwiftOnSecurity/sysmon-config@1836897…:sysmonconfig-export.xml:20,356`; https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon; https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/how-to-enable-sysmon; `olafhartong/sysmon-modular@082cba…:README.md:40` (all accessed 2026-10-08). ⇒ A parser must tolerate schema-version drift; pre-generated community configs may lag the newest Sysmon binary.

Provenance: https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/overview (accessed 2026-10-08). ⇒ Prefer XML-based parsing (documented by Microsoft as the reliable cross-language representation).

- **PROPOSED — TO BENCHMARK:** no official Microsoft or repo document provides event-volume/performance numbers (events/sec, CPU/disk cost per enabled event class, channel size). Any sizing numbers for Sentinel must be measured locally; none are asserted here.

## §SYSMON-5 — Exporting Sysmon events: `wevtutil` and EVTX mechanics

- **VERIFIED — documented export command:** `wevtutil` syntax includes `{epl | export-log} <Path> <Exportfile> [/lf:<Logfile>] [/sq:<Structquery>] [/q:<Query>] [/ow:<Overwrite>]` — "Exports events from an event log, from a log file, or using a structured query to the specified file"; worked example *(quote)*: `wevtutil epl System C:\backup\system0506.evtx`. Provenance: https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/wevtutil (accessed 2026-10-08).
- **VERIFIED:** `/ow:true` overwrites an existing export file without confirmation; `/q:` allows an XPath query to export a subset; `al | archive-log` archives a log "in a self-contained format". Provenance: same URL (accessed 2026-10-08).
- **INFERRED:** applying this to Sysmon — `wevtutil epl Microsoft-Windows-Sysmon/Operational C:\path\sysmon.evtx` — follows directly from the generic syntax; the docs' worked example uses the `System` log, not the Sysmon channel. (Syntax-level inference, high confidence, but no Sysmon-specific example in official docs.)
